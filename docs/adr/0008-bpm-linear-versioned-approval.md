# bpm v1：版本化线性审批链，业务自持表单

**Status**: accepted

bpm v1 只实现**线性有序审批链**：流程定义是一串节点，节点审批人按规则解析，通过前进、驳回结束、撤回在首个审批动作前、转办只换当前办理人。流程定义草稿可编辑，发布后不可修改，只能发新版本；实例在创建时锁定定义版本，在途实例不受新版本影响；同一 `key` 同时只有一个发布版本，发布新版本时旧版本自动停用。每个业务类型 v1 只使用一个默认 `key`，不做按金额/类别的流程路由。审批人规则限定为指定用户、角色、权限码、发起人、发起人部门负责人、指定部门负责人；角色/权限码节点为候选池，为每个候选人物化一条任务，任意一人办理后同节点其余任务取消。业务表单由业务模块自己持有（字段、校验、状态），bpm 只保存 `businessType + businessId + 标题/摘要快照`；实例通过/驳回/撤回时，bpm 在同一事务内调用业务注册的 `BusinessHandler`，业务状态与审批状态一起提交或回滚。

原因：这是一个单人全职项目，CRM 合同审批、请假、报销需要的都是有限链路的顺序审批，不是通用 BPMN。版本化保证审批历史可解释；候选池物化任务让「我的待办」「未读通知」「并发先办者胜出」都变成简单查询；业务自持表单避免动态表单引擎把校验、查询、统计全部复杂化；同事务回调避免业务与审批状态分叉。代价：角色/权限节点会为每个候选人产生任务行，小租户可接受；没有会签、条件分支、退回上一节点、BPMN 可视化；需要金额档路由时由业务侧按类别/金额选择不同 `key`，而不是在引擎里写表达式。未来加会签或条件节点可以在节点模式与规则层扩展，不需要推翻实例/任务/记录模型。

**替代方案**：继续用 CRM 的直通审批——没有多人链路、没有待办、没有不可变记录；引入完整 BPMN 引擎——单人维护成本与调试成本远超收益；动态表单引擎——表单数量有限、字段稳定，收益不足以抵消复杂度。
