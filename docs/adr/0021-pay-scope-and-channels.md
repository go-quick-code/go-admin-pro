# pay 范围与渠道策略：mock/wallet 先行，SPI 预留

**Status**: accepted

pay 按 L4 全量对齐芋道 8 域 14 表（app / channel / order / refund / transfer / notify / wallet×4 / demo×2），但 v1 只实现 mock 与 wallet 两个渠道：渠道 SPI 按芋道 PayClient 语义定形——统一下单、支付回调解析+验签、退款、退款回调解析+验签、转账（#137 追加的第五动作；v1 两渠道均同步完成，无异步解析动作，异步渠道回调随真实渠道实现接入），配置为渠道各自的多态结构；14 个芋道渠道码（wx×6、alipay×6、mock、wallet）全部保留为概念常量，微信/支付宝实现待有商户资源时另立工单。v1 中 pay 的唯一消费方是自带示例业务（示例订单、示例提现），ERP 收付款单与 CRM 回款接入另立里程碑。渠道凭证为平台级配置，应用与交易数据（订单/退款/转账/钱包/回调任务）为租户级，对齐 ADR 0010 的消息通道分层。凭证沿用仓库先例三段式：明文落库、查询脱敏 `******`、更新占位符合并，不引入加密。pay 不复用 ERP 单据内核与 doctype 注册表：回调驱动的异步状态机与「审核落账」单据形态不同，ADR 0018「等第二个消费者再提升」不因此触发。收银台为 admin SPA 内嵌页（照 OA 打卡页形态），不做独立 H5 站点。

原因：单人全职无商户资源，微信/支付宝代码写出来无法真实验收，是不可测的负资产；而渠道抽象是真设计——SPI 一次定形，补渠道实现时零改动。渠道凭证与消息渠道配置同构（平台级凭证、租户级使用），分层有 ADR 0010 先例可循。凭证不加密与全仓三处先例（message_channel、social_client、访问日志掩码）保持一致，key 放 configs 在单机部署下对 DB 泄露场景收益有限，风险在 pay 的强制安全审查中显式记录为「接受，全局加密另立工单」。

交易语义对齐芋道：支付订单支持多次部分退款（`refund_price` 累计不超过实付）；钱包支付下单即校验余额并直接扣减（无冻结/预占），余额不为负是不变量，退款原路回加；充值单是钱包充值的消费方，挂支付订单，充值禁用钱包渠道（自引用净零，防套利绕圈），挂套餐时按赠送金额入账，充值退款校验余额扣回后不为负；转账单 v1 仅 wallet（转入目标用户钱包）与 mock 渠道，示例提现为其消费方。mock 渠道下单不自动成功，提供模拟回调触发（成功/失败可选）走完整 notify 链路，本地可端到端演练回调重试、幂等与商户通知。商户回调为 `pay_notify_task` 表 + job 基建驱动：`RegisterSystem` 跨租户 handler 逐租户扫描到期任务，HTTP POST 商户回调地址（demo 端点本机自调用），按芋道间隔序列重试至上限后标记失败；渠道异步回调端点为平台级公开路由，真实性靠渠道验签（mock 触发端点除外，走管理端鉴权）；另设超时关单 job 收尾 WAITING 过期订单。错误码跟随 ERP/OA 现状用 HTTP 语义（`xerr`），不引入 pay 数字段。

拒绝的替代：把微信/支付宝实现一并写出（不可测）；pay 专属 AES 加密（破坏仓库一致性、单机收益有限）；只留 mock 渠道不建 SPI（渠道抽象是芋道 pay 的核心概念，砍掉违背概念等价）；复用 doc kernel（状态机与事务边界形态不同）；钱包挂 member 用户并顺手引入 member（范围事故，表结构 `user_id + user_type` 已零成本预留）。

相关：ADR 0003（L4 全量范围策略）、ADR 0007（Money 值类型）、ADR 0010（平台级渠道/租户级日志先例）、ADR 0018（单据内核边界）。
