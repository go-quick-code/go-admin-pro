## Problem Statement

这个项目要用 Go 重写芋道（ruoyi-vue-pro）的后台框架，但当前只完成了平台骨架：认证、RBAC、多租户、基础 infra 和代码生成。它离承接真实业务还有结构性缺口：DDL 缺少 `creator/updater`，数据范围枚举的非法值会回退成「全部」（越权风险），租户插件在无租户上下文时 fail-open，没有 Excel 能力，也没有版本化迁移。

作为项目所有者，我需要先交付 CRM 业务套件，用它来验证平台骨架是否真的能承载业务：客户、联系人、跟进记录、商机、合同、回款计划与回款记录、产品、仪表盘，加上公海和负责人数据权限。CRM 必须一次交付完整套件，而不是只做一个切片；前端自建，不追求与芋道的 API/DDL 兼容。

## Solution

分两段推进：

1. **底座冲刺**：引入 goose 版本化迁移；实体表补 `creator/updater`；数据范围枚举对齐芋道 1–5 并禁止非法值回退；租户插件改 fail-closed；CORS 改 allowlist；用户/租户创建加事务；引入 Excel 导入导出 helper；修正 README 与代码不一致的三处描述。

2. **CRM 套件**：9 个业务实体加 3 张支撑表；公海支持释放、认领、30 天无跟进自动回收；数据权限采用「角色范围上限 + 负责人归属 + 自定义部门并集」；合同走状态机，审批先用 `ApprovalService` 直通实现；回款分计划与记录两层；仪表盘做 4 个卡片和 2 张图；客户/联系人/产品支持 Excel 导入，客户/合同/回款支持导出；前端自建 Vue 页面。

施工顺序：底座冲刺 → 手写客户 + 联系人确立模式 → 升级 codegen → 生成其余实体 → 仪表盘 → 硬化。里程碑仍是一个，不切对外版本。

## User Stories

1. 作为开发者，我想要版本化迁移，这样每次表结构变更都可审计、可回滚。
2. 作为系统管理员，我想要现有数据在补 `creator/updater` 时不丢失，这样升级不会破坏已有租户。
3. 作为租户管理员，我想要非法的数据范围值返回 400，而不是回退成「全部」，这样不会意外扩大可见数据。
4. 作为系统管理员，我想要租户表在缺少租户上下文时直接报错，这样后台任务不能绕过租户隔离。
5. 作为开发者，我想要 CORS 使用 allowlist，这样只有受信任的源能调用 API。
6. 作为租户管理员，我想要用户创建、租户创建和角色菜单分配是事务性的，这样失败不会留下半套数据。
7. 作为开发者，我想要 Excel 导入导出 helper 带表头映射与逐行校验，这样 CRM 各实体能复用同一套导入导出。
8. 作为开发者，我想要 README 与代码一致，这样新贡献者不会被 demoJob、字典缓存、codegen 的描述误导。
9. 作为销售，我想要只看到我负责的客户，这样我的跟进列表不会被别人的客户淹没。
10. 作为销售，我想要按角色数据范围看到本部门或本部门及以下的客户，这样我能覆盖团队业务。
11. 作为销售主管，我想要看到下级部门的客户与商机，这样我能做团队管理。
12. 作为租户管理员，我想要给角色配置自定义部门范围，这样跨部门团队可以共享数据。
13. 作为拥有多个角色的用户，我想要可见部门取并集，这样权限叠加符合直觉。
14. 作为销售，我想要联系人、跟进记录、回款记录跟随父记录的可见性，这样关联数据不会越权泄露。
15. 作为销售主管，我想要负责人转移留下历史记录，这样客户归属变化可追溯。
16. 作为租户管理员，我想要数据范围修改后立即生效，这样不用重启服务。
17. 作为销售，我想要维护产品分类和产品，这样商机和合同可以引用统一的产品。
18. 作为销售，我想要从 Excel 导入产品，这样初始化产品库不用逐条录入。
19. 作为销售，我想要导出产品列表，这样能离线整理价格。
20. 作为租户管理员，我想要产品编码在租户内唯一，这样不同团队不会重复建产品。
21. 作为销售，我想要创建和编辑客户，填写行业、级别、来源、电话、地址等信息，这样客户档案完整。
22. 作为销售，我想要客户列表支持分页、按名称/负责人/状态/部门筛选，这样能快速定位客户。
23. 作为销售，我想要客户详情页带联系人、跟进、商机、合同 tab，这样所有关联信息在一个页面。
24. 作为销售，我想要从 Excel 导入客户，校验失败时返回行号和原因，这样批量导入可控。
25. 作为销售，我想要导出客户列表且导出内容遵守数据权限，这样不会把别人的客户导出去。
26. 作为销售，我想要把客户释放到公海，这样长期不跟进的客户能回到公共池。
27. 作为销售，我想要从公海认领客户，并受认领上限约束，这样不会有人囤积客户。
28. 作为销售主管，我想要客户超过 N 天无跟进自动回收到公海，但有未作废合同的客户除外，这样活跃业务不会被误回收。
29. 作为销售主管，我想要每次领取、释放、转移、自动回收都记录负责人历史，这样归属纠纷可查。
30. 作为租户管理员，我想要按租户配置公海回收天数和认领上限，这样不同团队可以有自己的规则。
31. 作为销售，我想要在客户下维护多个联系人，记录职位、电话、邮箱、决策角色，这样对接人信息清晰。
32. 作为销售，我想要记录跟进记录，选择电话/拜访/微信/邮件/其他，填写内容和下次跟进时间，这样跟进过程可回溯。
33. 作为销售，我想要新增跟进后客户的最后跟进时间自动刷新，这样公海回收规则准确。
34. 作为销售主管，我想要查看客户、商机、合同下的跟进历史，这样能复盘销售过程。
35. 作为销售，我想要创建商机，填写阶段、预计金额、预计成交日期和产品行项目，这样商机可量化。
36. 作为销售，我想要推进商机阶段并标记赢单/输单，这样销售漏斗准确。
37. 作为销售主管，我想要看到按阶段聚合的商机数量与金额漏斗，这样能识别卡点。
38. 作为销售，我想要从商机或直接创建合同，填写合同号、金额、签订日期、起止日期、产品行项目和附件，这样合同信息完整。
39. 作为销售，我想要合同有行项目时金额必须等于行项目合计，这样金额不会被手工改乱。
40. 作为销售，我想要提交合同审批，v1 由有权限的人直接改状态，bpm 上线后再接真实审批，这样 CRM 不被 bpm 阻塞。
41. 作为销售主管，我想要审批通过或驳回合同，这样合同状态可控。
42. 作为财务，我想要存在回款记录的合同不能作废，这样已发生的收款不会被抹掉。
43. 作为财务，我想要按合同创建多期回款计划，填写期数、金额、到期日，这样应收节奏清晰。
44. 作为财务，我想要回款计划合计不超过合同金额，回款记录合计不超过计划金额，这样金额不变量始终成立。
45. 作为财务，我想要登记回款记录，填写金额、收款日期、收款方式和备注，这样实际到账可追踪。
46. 作为财务，我想要回款计划状态由已收金额和到期日派生，分为待回款/部分回款/已回款/逾期，这样不需要手工维护状态。
47. 作为财务，我想要导出回款计划，包含已收金额和逾期标识，这样能做对账。
48. 作为销售主管，我想要仪表盘有客户总数、进行中商机金额、已签合同金额、逾期回款四个卡片，这样一眼看到团队盘子。
49. 作为销售主管，我想要商机阶段漏斗和近 12 个月合同/回款趋势两张图，这样能看趋势。
50. 作为销售，我想要仪表盘指标按我的数据权限过滤，这样每个人看到的是自己的盘子。
51. 作为开发者，我想要客户和联系人先手写，沉淀 model/dto/repository/service/api/权限/菜单/Vue/测试的统一模式，这样后续实体有可复制的样板。
52. 作为开发者，我想要 codegen 升级后能生成上述模式，这样产品、商机、合同、回款、跟进可以批量生成再补业务规则。
53. 作为开发者，我想要 HTTP 层的集成测试覆盖权限、租户隔离和金额不变量，这样高风险路径有回归保护。
54. 作为开发者，我想要纯函数单测覆盖数据范围组合、金额校验、编号和状态机，这样组合爆炸的场景能快速定位。
55. 作为开发者，我想要所有 CRM 表都带 `tenant_id`、`creator/updater` 和软删除，这样平台能力对业务模块一致生效。
56. 作为开发者，我想要客户、商机、合同、回款都使用统一编号规则（前缀 + 日期 + 序号），这样单号可读且租户内唯一。
57. 作为系统管理员，我想要 CRM 的菜单和按钮权限由种子下发，这样新租户开箱即可用。
58. 作为租户管理员，我想要 CRM 数据按租户隔离，这样不同租户的客户和合同互不可见。

## 实现与测试

- 新增 `crm` 业务模块（model / dto / repository / service / api 分层），新增 Excel 能力包；迁移与 `BaseEntity` 在平台层完成。
- 表结构、数据权限谓词、公海规则、金额不变量、状态机、编号、删除约束、API 清单、前端页面、导入导出与测试 seam，以 [`docs/crm-mvp-spec.md`](../crm-mvp-spec.md) 为唯一来源；本文件不再复制规则正文。
- 架构取舍见 `docs/adr/0001`–`0005`。

## Out of Scope

- OA 领域模型（公告、考勤、请假/报销、日程、会议室、文档）——CRM 交付后单独一轮。
- bpm 引擎实现——只定义 `ApprovalService` 接口和 v1 直通实现。
- 线索（Lead）、订单、库存、多币种、汇率。
- 跟进提醒、公海回收通知等消息能力。
- 芋道 API/DDL/前端的 drop-in 兼容（兼容契约为 C1 概念等价）。
- 其他 L4 套件：mall、erp、mp、pay、report、ai。
- 复杂报表/BI；仪表盘只做 4 卡片 + 2 图。
- codegen 的详细设计——客户+联系人完成后单独一轮。
- 本地磁盘之外的附件存储（OSS/S3）；合同附件复用 `infra_file`。
- 移动端与对外 OpenAPI。

## Further Notes

- 术语以 `GLOSSARY.md` 为准：客户、联系人、商机、合同、回款计划、回款记录、跟进记录、产品、负责人、公海；避免使用「线索」「订单」「商品」。
- 架构决策见 `docs/adr/0001`–`0005`：C1 兼容契约、Go/GORM 模型底座、L4 范围策略、数据权限模型、goose 迁移。
- 详细设计见 `docs/crm-mvp-spec.md`；本 issue 是面向 tracker 的规格摘要。
- 假设：全职单人、无交付期限、自建前端、模块化单体。
- 风险：全 CRM 一次交付意味着反馈周期长，用内部演示、集成测试和真实使用来抵消；数据权限是最高风险区，先用测试矩阵锁住。
- 开放项：行业/来源/客户级别/跟进类型/回款方式的字典种子在实现时提案；OA 与 codegen 详细设计另开一轮。
