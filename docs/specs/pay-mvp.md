# pay MVP：支付（应用 / 渠道 / 订单 / 退款 / 转账 / 回调 / 钱包 / 示例）

## Problem Statement

平台底座、CRM、OA、ERP 已交付，单据内核与注册表也收口完毕，但项目对标的芋道套件清单里还差 pay：作为单人全职的长期能力对标项目，下一个里程碑需要支付域——渠道抽象、支付/退款/转账单据、回调通知与钱包。项目没有 mall/member，pay 的天然消费方缺位，但这不影响先建基础设施：示例业务自闭环验证全链路，业务套件接入另立里程碑。

## Solution

一次交付全量对标芋道 pay 的八域 16 表：支付应用（+渠道绑定）、支付订单（+发起尝试）、退款单、转账单、回调通知（任务+日志）、钱包（余额/流水/充值单/充值套餐）、示例业务（示例订单/示例提现）、渠道 SPI。v1 只真实现 mock 与 wallet 两个渠道，14 个芋道渠道码全部预留（ADR 0021）；施工顺序：骨架+应用渠道 → 订单+收银台 → 钱包域 → 回调通知 → 退款 → 充值套餐 → 转账+示例提现 → Excel/演示/验收。

## User Stories

1. 作为租户管理员，我想要创建支付应用（app_key + 三类商户回调地址），这样每个业务场景有独立接入身份。
2. 作为租户管理员，我想要在应用详情里绑定该应用可用的渠道码，这样收银台只出现已开通的支付方式。
3. 作为平台管理员，我想要平台级渠道配置页（14 渠道码常驻、凭证 JSON 脱敏三段式），这样凭证一处管理、应用侧只引用。
4. 作为消费方服务端，我想要按 merchant_order_id 幂等下单（重复提交返回原单），这样重试不会产生重复订单。
5. 作为用户，我想要在收银台看到订单与可用渠道、发起支付并看到结果，这样支付动作有明确入口。
6. 作为用户，我想要钱包渠道支付下单即扣余额（不足 409），这样付款即时到账、无挂账。
7. 作为开发者，我想要钱包余额只经唯一入账入口变动（行锁+非负 SQL 双保险、流水快照结存），这样余额可由流水重放验证。
8. 作为用户，我想要「我的钱包」与「我的流水」自助页，这样随时知道余额与每笔增减。
9. 作为演示者，我想要 mock 渠道下单后手动触发模拟回调（成功/失败可选），这样本地就能演练真实渠道回调的全链路。
10. 作为开发者，我想要渠道回调走平台级公开端点（渠道验签+状态认领幂等），这样重复/伪造回调不会重复入账。
11. 作为消费方，我想要支付/退款/转账成功后由任务表按固定间隔序列重试回调我（15/15/30/180/1800×3/3600 秒，共 9 次），这样瞬时故障不影响最终通知。
12. 作为消费方，我想要回调报文带 HMAC 签名且密钥缺失时 job 拒发（fail-closed），这样回调不可伪造。
13. 作为财务，我想要订单支持多次部分退款且累计不超实付（全额退完订单置已退款），这样退款口径可控。
14. 作为财务，我想要钱包渠道退款原路回加余额并留流水，这样退款有账可查。
15. 作为用户，我想要按充值套餐充值（支付金额+赠送金额入账），且充值不能用钱包渠道（防自引用套利），这样充值语义干净。
16. 作为财务，我想要充值退款时校验余额扣回后不为负，这样钱包不会负资产。
17. 作为租户管理员，我想要转账单（wallet/mock 渠道）把资金转入用户钱包并回调通知，这样出账有单据。
18. 作为管理员，我想要示例提现申请→审批→转账→回调联动，这样转账域有端到端消费方。
19. 作为管理员，我想要超时未支付的订单被 job 自动关闭，这样挂单不无限悬挂。
20. 作为租户管理员，我想要支付订单/退款/转账/钱包流水列表 Excel 导出，这样离线对账方便。
21. 作为开发者，我想要金额沿用 Money（ADR 0007）、单号 ZF/TK/ZZ/LS 前缀+日期+序号（客户端伪造不采纳），这样与 CRM/ERP 资金口径一致。
22. 作为开发者，我想要 pay 不依赖 crm/erp/oa/bpm、不复用单据内核（异步回调状态机形态不同，ADR 0021），这样两套生命周期互不拖累。
23. 作为开发者，我想要渠道 SPI 照芋道 PayClient 四动作定形（下单/支付回调解析验签/退款/退款回调解析验签），这样补真实渠道实现时零改动。
24. 作为开发者，我想要 HTTP 集成测试覆盖并发双扣/回调幂等/重试序列/部分退款累计/越权矩阵/签名伪造，这样高风险路径有回归保护。
25. 作为运维，我想要空库迁移往返校验 EXPECTED_TABLES=116、租户表登记强校验通过（pay_channel 平台级），这样升级可审计。
26. 作为演示者，我想要 make run-demo 一键重建支付全链路演示数据（下单→模拟回调→商户回调→退款→充值→提现），这样演示不用手工造数。
27. 作为租户管理员，我想要 pay 菜单与按钮权限由种子下发、普通角色默认不授予（资金敏感），这样新租户开箱即用且敏感页可控。
28. 作为安全，我想要渠道凭证查询脱敏、公开端点限速、金额全部服务端定、日志不落凭证，这样支付域攻击面有明确防线。

## 实现与测试

- 新增 `internal/module/pay`（api/dto/model/repository/service 五层 + `service/channel/` 渠道 SPI），表 16 张（应用渠道 3、交易 5、回调 2、钱包 4、示例 2），`EXPECTED_TABLES` 100→116；迁移 00035 起按域拆 4 个；菜单 seed 800 段，普通角色默认不授 pay；job 种子 `payNotifyRetry`（每分钟）+ `payOrderTimeoutClose`（每 5 分钟）。
- 状态机（订单 0/10/20/30、退款 0/10/20、转账 0/5/10/20、回调 0/10/20/21/22）、渠道 SPI、钱包唯一入账、退款累计、回调重试序列、充值禁钱包渠道、转账入账、删除约束、数据权限与自助端点、API 清单、前端 11 页、测试矩阵，以 [`docs/pay-mvp-spec.md`](../pay-mvp-spec.md) 为唯一来源；本文件不复制规则正文。
- 架构取舍见 ADR 0021（范围与渠道策略）；分层先例 ADR 0010（平台级凭证/租户级数据）、0019（租户表登记）。

## Out of Scope

- 微信/支付宝渠道实现（SPI 预留，待商户资源另立工单）；业务套件接入（ERP 收付款/CRM 回款对接收银）；member 会员与 C 端；独立 H5 收银台。
- 多币种（单币种人民币）；手续费计算（字段保留恒 0）；渠道凭证加密（明文+脱敏先例，风险显式接受）；回调手动重发；钱包手动调余额（`UPDATE_BALANCE` 枚举预留）。
- 芋道 API/DDL/前端 drop-in 兼容（契约 C1）。

## Further Notes

- 术语以 `GLOSSARY.md` pay 段为准（pay、支付应用、支付渠道、钱包、示例业务、支付订单、退款单、转账单、回调通知任务、商户回调、钱包流水、充值单、充值套餐、收银台）；避免：付款单（ERP 采购资金单据）、结算账户（ERP 线下资金账户）、租户套餐（平台授权）、退货单（ERP 数量退回）。
- 对芋道的主动差异（实施 PR 描述需列出）：`pay_channel` 平台级 + `pay_app_channel` 绑定表（芋道每应用各配渠道）；新增 `pay_sequence`；drop `channel_id` 只存 `channel_code`；钱包无 `freeze_price`（无冻结语义）；转账无平台资金账本；无手动调余额/手动重发入口；错误码 HTTP 语义；单号前缀 ZF/TK/ZZ/LS；`UPDATE_BALANCE` 枚举预留无入口。
- 芋道事实依据：master 源码核实（8 域 14 表 DO、渠道枚举 14 码、`NOTIFY_FREQUENCY={15,15,30,180,1800,1800,1800,3600}` 首次+8 重试、订单 refund_price 部分退款、钱包 biz_type 六类、demo 提现状态机）。
- 假设：全职单人、串行施工、模块化单体、自建前端；本地无真实商户资源，mock/wallet 即全部可测渠道。
- 风险：回调链路（异步 job + 自调用 + 重试）是时序最复杂区——用任务状态认领幂等 + 重试序列表驱动测试 + mock 全链路集成测试锁住；钱包并发用 SQL 双保险 + 并发双扣测试锁住。
